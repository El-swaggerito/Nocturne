# Nocturne AI agent: Issue #8

This folder creates **untrusted, validated invoice proposals**, not payment permissions. It contains no wallet, NEAR RPC signing code, transaction execution, or key management.

## Verified integration choice (4 November 2026)

- Runtime: Node.js >= 22.16.0; TypeScript 5.8.3.
- Inference API: NEAR AI Cloud, OpenAI-compatible Chat Completions **v1**, `https://cloud-api.near.ai/v1/chat/completions`.
- Model: `deepseek/deepseek-v3.2` (text-capable, explicitly advertised by NEAR AI Cloud).
- SDK: OpenAI TypeScript SDK **7.15.0**, used only for the compatible Chat Completions endpoint; it is not an OpenAI API subscription/key.
- Schema validator: Zod **4.6.5** (strict runtime objects).
- Credential: `NEAR_AI_KEY` environment variable for NEAR AI Cloud; **not** any NEAR wallet private key. The API URL is fixed in code so that an accidental environment override cannot redirect your API credential.
- The default model is text-only in this MVP. Images and PDFs are not implemented. Verify selected models against NEAR AI Cloud's live model catalogue before upgrades.

Sources: https://near.ai/models/deepseek/deepseek-v3.2 and https://near.ai/pricing

## Install, typecheck, test

From the repository root:

```sh
cd agent
npm install
npm run typecheck
npm test
```

Tests contain only fictional values; they do not invoke the remote model or need an API key. Commit `agent/package-lock.json` generated by `npm install` to pin the resolved dependency tree. `dist/` and `node_modules/` are already ignored by the repository's `.gitignore`.

## Configure and run live smoke test

At the **repository root**:

```sh
cp .env.example .env
```

Replace the placeholder `NEAR_AI_KEY` in your local `.env` file with a real NEAR AI Cloud key. From `agent/`:

```sh
npm run smoke
```

This reads `fixtures/valid-invoice.txt` and makes a paid inference call. The fixture is fictional. A representative *successful* result is:

```json
{
  "status": "validated",
  "proposal": {
    "recipient": "merchant.testnet",
    "amountYoctoNear": "1500000000000000000000000",
    "invoiceReference": "INV-2026-0001",
    "validationErrors": []
  }
}
```

Model outputs can vary. A real completion may be invalid and be rejected. Do not use private invoices with the demonstration CLI because it prints a validated proposal to stdout.

To check the missing-key path, leave `NEAR_AI_KEY` unset or use the placeholder, and run `npm run smoke`. It fails with a clear message and does not print a credential.

## Trust boundaries

1. All invoice text is sent as one **user** message. The constant **system** message is never populated from an invoice.
2. Model output is parsed as a **single JSON object**, not markdown, and Zod strict objects reject both top-level and nested unknown properties.
3. The model emits a NEAR decimal string, not yoctoNEAR. Local BigInt conversion accepts at most 24 fractional digits and checks the NEAR `u128` bound. Non-NEAR currencies, bad NEAR account IDs and zero or malformed amounts are rejected.
4. Missing/ambiguous information is represented by explicit model-reported `validationErrors`, which cause the proposal to be rejected. These messages themselves are not trusted instructions.
5. Provider failures and truncation cause explicit errors. Credentials, full provider errors and input invoices are not written to logs by inference code.
6. A validated `InvoiceProposal` is **not** authorisation to pay. Future contract-side spending controls and owner/agent key restrictions are separate requirements in issues #2, #4, #6 and #9.

**Limitations:** Schema validation cannot independently establish that extracted values truly match the invoice. Model hallucination, prompt injection or incorrect extraction remain possible even with a valid JSON object. Issue #9 should add deterministic source-field checks, ambiguous/adversarial fixtures and model-evaluation evidence, with no automatic payment on uncertainty. Do not use model output to set owner IDs, function-call key scopes or policy limits.
